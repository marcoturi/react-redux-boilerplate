# Unit and component tests (Vitest 5, Testing Library, MSW 3)

- Vitest runs two projects (`vite.config.mts`): `unit` runs `src/**/*.spec.ts` (store, selectors, helpers) in jsdom with `src/test/unit.setup.ts` and the MSW Node `server`; `browser` runs `src/**/*.spec.tsx` (components, pages, routes) in a real Chromium through Playwright (Vitest browser mode) with `src/test/browser.setup.ts` and the MSW service `worker`, the same one the dev server uses. The file extension decides the project: a spec that renders JSX is `.tsx`. Chromium must be installed once (`pnpm exec playwright install chromium`) for `pnpm test`.
- Put tests next to the code they test, as `<file>.spec.ts` or `<file>.spec.tsx`. Only specs carry that suffix: the files they share live in two folders, both left out of the build and of coverage. `src/test/` holds what only tests use: render helpers (`render.tsx`), storage helpers, the Vitest setup files. `src/mocks/` holds MSW, which the dev server uses too: handlers, the `worker` (`browser.ts`), the Node `server` (`node.ts`), `initMocks`, and the mock data in `src/mocks/data/<feature>.ts`, shared by the handlers and the specs. Only `initMocks` may be imported by app code, from `main.tsx`.
- Vitest globals (`describe`, `test`, `expect`, `vi`) need no import. Write `test`, not `it` (Biome `useConsistentTestIt`).
- Prefer integration tests that render components with `renderWithProviders` from `@/test/render`. It creates a fresh store and an in-memory data router for each test, so router hooks such as `useNavigation` work; pass `route` for URL-dependent UI. Render the app's route tree, loaders included, with `renderRoutes(createRoutes, { route })`. Never import the app's singleton `store`. To check the UI after dispatching a request yourself (e.g. a refetch that fails), wrap the dispatch in `actAndFlush` from the same file: RTK Query notifies the UI on the next animation frame.
- Unit-test only complex reducers and selectors: call `reducer(state, action)` directly, or build the state with `setupStore(preloadedState)` from `@/shared/store`, dispatched actions and `await store.dispatch(api.util.upsertQueryData(...))`. Do not cast partial objects `as RootState`.
- Both setup files answer a request without a handler with an error instead of letting it reach the network, and fail the test even when the code hides that error. Their `onUnhandledFrame` callback (`failUnhandledFrame` in `src/test/msw-unhandled.ts`, the MSW 3 name of `onUnhandledRequest`) records the request and throws: with a callback, MSW sends the request to the real network unless it throws. Same-origin requests pass, because in the browser the page loads its own modules from the Vitest server; keep the API on another origin. `afterEach` and `afterAll` assert that no request was recorded. The setup files also clear localStorage after each test; Testing Library unmounts after each test by itself. Real browser APIs need no stubs: do not add jsdom workarounds to the browser setup.
- Mock the network only with MSW: shared handlers in `src/mocks/handlers/` (URLs built from `env.API_URL`), one-off responses with `worker.use(...)` inside a `.spec.tsx` (`worker` from `@/mocks/browser`) or `server.use(...)` inside a `.spec.ts` (`server` from `@/mocks/node`), `{ once: true }` to fail only the first request. For a failed request use the factory of the feature's handler file (`subscriptionsFailOnce()`, `usersFailOnce()`, built on `serverErrorOnce(url)`), and add one there for a new endpoint: a `once` handler stays used after its first match, so a shared instance would be skipped. Never mock hooks, selectors or `fetch`; mock a module only at the edge of the app (Sentry, `captureError`).
- Read and write persisted settings with `readStoredSetting(key)` and `writeStoredSetting(key, raw)` from `@/test/storage`, never with hand-built localStorage keys.
- Cover failures, not only the happy path: an API error through `worker.use` or `server.use`, corrupt or missing localStorage data.
- Type handler responses and mock data with the domain types (`satisfies User`, `SubscriptionType.OneTimePurchase`), so mocks cannot drift from the API types.
- Query by role, label or text (`getByRole` first); use `getByTestId` only as a last resort. The `data-testid` attributes are mainly for e2e.
- Wait for the UI with `findBy*` rather than `waitFor(() => getBy*)`; inside `waitFor` keep one assertion and no side effects. Never wait with timeouts.
- Call `userEvent.setup()` before `render`, and await every `user.*` call and every dispatched thunk.
- In a test that uses fake timers together with `findBy*` or `userEvent`, use `vi.useFakeTimers({ shouldAdvanceTime: true })` and `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })`, otherwise they hang; plain `vi.useFakeTimers()` is fine for code without them. To fix only the date, `vi.setSystemTime()` alone is enough. Never assert on the real current date.
- Make each test create its own data; never depend on test order or on state left by another test. Create the store inside each test (`const store = setupStore()`, or a seeding helper such as `storeWithSubscriptions(data)`) rather than in a `let` assigned by `beforeEach`; if a `let` is unavoidable, type it as `AppStore` (`@/shared/store/types`) instead of suppressing `noImplicitAnyLet`.
- Investigate a flaky test with `pnpm vitest run <file> -t "<name>"` and `--sequence.shuffle`; do not add retries.
- Run `pnpm test` before finishing. `pnpm test:coverage` measures `src/` except entry points, test helpers and `src/UI/Base`, and fails under the thresholds in `vite.config.mts`, as CI does: add tests rather than lowering them.
